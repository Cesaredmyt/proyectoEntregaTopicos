## 1. Clasificar la plataforma actual

```
  Navegador (formulario recomendar.html)
        |
        |  fetch("/entregas/recomendar/")  -> POST con JSON
        v
 ┌───────────────────────────────────────────┐
 │ Un solo Django (plataforma-entregas)      │
 │ python manage.py runserver  (puerto 8000) │
 │                                           │
 │ views.py -> recomendador.py -> reglas.py  │
 │                    |                      │
 │                    v                      │
 │             medios.py   + .joblib         │
 └───────────────────────────────────────────┘
```

- Cliente: el navegador con la página `recomendar.html` (o cualquier cliente que mande JSON, como Flutter o curl).
- Proceso en el servidor: un solo Django (en el repo se arranca con gunicorn dentro de Docker, y en clase con `manage.py runserver`).
- URL que usa el front: `/entregas/recomendar/`.

Es un **monolito + API**. La evidencia es que toda la lógica vive en un solo proyecto: en `views.py` la vista llama directo a `obtener_recomendador(...)` y a `crear_medio(...)` con un simple `import`, y el modelo se carga desde la carpeta `entregas/modelo/` del mismo proyecto. Solo hay un `Dockerfile` y una imagen. Aunque el `docker-compose.yml` levanta tres copias de `web` detrás de nginx, son tres copias del mismo código y no tres servicios distintos, así que es escalar el monolito.

## 2. La trampa de los endpoints

No. Que existan `/entregas/hola/` y `/entregas/recomendar/` solo quiere decir que hay varias rutas, pero las dos las atiende el mismo Django, en el mismo proceso y con el mismo despliegue. Es como tener varias ventanillas en la misma oficina: el cliente ve mostradores distintos, pero el edificio y la caja son los mismos. Separar el HTML del servidor es lo que hace una API: separa al cliente del servidor. Los microservicios van más allá, porque separan unos servidores de otros: procesos distintos, que se despliegan por separado y se hablan por red. Si se cae o se reinicia Django, se caen las dos rutas a la vez, y eso muestra que no son servicios independientes.

## 3. La misma operación en dos mundos

**Hoy (monolito + API), paquete a las 3:00:**

1. El cliente manda un solo POST a `/entregas/recomendar/`.
2. Entra la vista `views.recomendar`, que valida los campos.
3. La vista llama a `obtener_recomendador("arbol").explicar(paquete)`. Esto es un `import` normal, todo pasa en memoria.
4. Dentro, el modelo prefiere dron, pero `reglas.es_posible` lo descarta porque a las 3:00 es de noche. Se queda con la moto.
5. La vista llama a `crear_medio("moto").planear(paquete)` y arma el JSON con el medio, el motivo y el plan.

Solo hay una llamada de red (cliente → servidor). Si el modelo falla, falla toda la petición.

**Si el recomendador fuera otro servicio:**

1. Cliente → Gateway → servicio de Pedidos (primer salto de red).
2. Pedidos → servicio Recomendador, con un `POST http://recomendar/sugerir` (segundo salto de red).
3. El Recomendador usa el modelo y las reglas, y responde `{"medio": "moto", ...}`.
4. Pedidos recibe la respuesta, arma el plan con `medios.py` y le contesta al cliente.

La diferencia es que antes era un `import` que siempre estaba ahí, y ahora es una llamada HTTP que puede tardar o fallar. Si el Recomendador no responde, Pedidos tiene que decidir qué hacer: rechazar el pedido, usar un medio por defecto (por ejemplo moto o camioneta) o dejarlo en cola para reintentar más tarde.

## 4. Decisión de la empresa

**Postura recomendada: extraer solo el servicio de IA.**

1. **Cambian a ritmos distintos.** El Random Forest se reentrena cada semana, y los pedidos casi no cambian. Con un servicio aparte, actualizar el modelo no obliga a reiniciar ni redesplegar toda la plataforma.
2. **Pesa mucho.** Son unos 50 MB que hay que cargar en memoria. Separarlo permite darle sus propios recursos y escalarlo sin tener que escalar todo lo demás.
3. **Es poco costo y mucho beneficio.** Partir todo (pedidos, notificaciones, etc.) sería mucha infraestructura y complejidad para un equipo pequeño, sin una necesidad real todavía. Con un solo corte se gana lo que hace falta y el resto sigue siendo sencillo.

## 5. Un solo corte

**Modelo propuesto:** el servicio de recomendación.

- **Qué se lleva:** `recomendador.py`, los archivos `.joblib` (son suyos y se actualizan solos) y también `reglas.py`, porque el recomendador la usa en cada decisión y así no hay que hacer una llamada de red por cada medio que se revisa.
- **Qué se queda en el backend de pedidos:** la vista (`views.py`), la entrada HTTP y `medios.py`, porque armar el plan de entrega (minutos, indicación) es parte del negocio de pedidos, no del modelo.
- **Por qué este corte y no un servicio por archivo:** porque `recomendador.py`, `reglas.py` y los `.joblib` siempre cambian juntos y se usan juntos. Si cada archivo fuera un servicio, una sola recomendación tendría varios saltos de red, más fallas posibles y más cosas que desplegar, sin ninguna ganancia. Un solo corte separa lo que cambia distinto (la IA) de lo que casi no cambia (pedidos) y nada más.
